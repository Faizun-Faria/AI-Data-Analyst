# Decision log

Newest decisions are added at the bottom. A reversed decision stays in the log, and a new entry records the reversal.

| ID | Date | Decision | Why | Alternatives considered |
| --- | --- | --- | --- | --- |
| D-001 | 2026-10-24 | Build an AI data analyst over complaints data, with an audited warehouse and a semantic layer underneath it. | AI that a regulated business can audit; one build shows data engineering, analytics engineering, AI and BA work. | A BI dashboard only; a chatbot over raw tables. |
| D-002 | 2026-10-24 | Use the CFPB narratives archive as the main dataset and replay its 21 exports in order, one batch per export. | The CFPB stopped publishing narratives in August 2026, so the archive is fixed; replaying exports gives a realistic incremental-ingestion story. | The live complaints API, which no longer carries narratives. |
| D-003 | 2026-10-24 | DuckDB for the warehouse. | Fast local analytics, free, no server, installs with pip. | Postgres (a server to run); Snowflake or BigQuery (accounts and cost). |
| D-004 | 2026-10-24 | dbt Core with `dbt-duckdb` for transformations. | Tests, documentation and lineage in the industry-standard tool. | Plain SQL scripts. |
| D-005 | 2026-10-24 | A semantic layer of YAML metric and dimension definitions that the AI reads before writing SQL. | The AI uses precise, documented definitions instead of guessing from raw tables. | Let the model read raw table schemas. |
| D-006 | 2026-10-24 | Parse every generated query with sqlglot; allow only read-only queries on allowlisted tables. | Generated SQL can't change data or reach outside the defined tables, and every block can be explained. | A read-only database user alone. |
| D-007 | 2026-10-24 | No Docker: everything installs with pip or runs in the cloud. Prefect on Windows, Airflow standalone on Mac or Linux. | One-command setup on an ordinary laptop. | Docker Compose for the whole stack. |
| D-008 | 2026-10-24 | MVP is phases 0-5, scoped to one product and the last five years, and is published at the MVP gate. | A working, tested analyst in about 50-70 hours. | Build all nine phases before publishing. |
| D-009 | 2026-10-24 | Keep the FSPO document layer off until its terms of use are checked for bulk download; use a sample if anything is unclear. | Respect the publisher's terms. | Bulk-download straight away. |
| D-010 | 2026-10-24 | Never send complaint narratives to an LLM provider that trains on inputs; check the API's data-use terms first. | Keeps consumers' own words out of third-party training data. | Any provider. |
| D-011 | 2026-10-27 | The raw zone is a local folder by default, and S3 when `QUERY_CF_RAW` is an `s3://` URI. Both use the same `<source>/<batch_id>/<file>` layout. | The pipeline and its tests run without an AWS account; S3 is a setting, not a rewrite. | S3 only. |
| D-012 | 2026-10-27 | Audit every ingestion attempt, not only successes, and derive the batch ID from the export's SHA-256. | A crash or failure leaves a trace; identical bytes can't land twice, so re-runs are safe. | Random batch IDs; audit successes only. |
| D-013 | 2026-10-27 | Count rows with a CSV parser, not by counting lines. | Narratives hold line breaks inside quoted fields, so line counts overstate rows. Checked on the August 2026 export: the parser count matches DuckDB's `read_csv` count. | `wc -l`-style line counts. |
| D-014 | 2026-10-27 | An export whose columns differ from the config still lands, flagged in `ingestion_audit.columns_match`. | The raw zone keeps exactly what was delivered; the warehouse tests decide what is usable. | Reject the export at ingestion. |
| D-015 | 2026-10-27 | Load the whole archive into the warehouse; apply the MVP scope (one product group, last five years) from phase 3. | 17.5 million rows fit DuckDB on a laptop; the Wells Fargo showcase question needs 2011-2016 data; narrowing later is a setting, not a rebuild. | Load only credit cards from the last five years. |
| D-016 | 2026-10-27 | Accept complaints received up to 2026-08-31, not 2026-08-14 as the archive page states. | The profile found 361,832 complaints received 15-31 Aug 2026 in export 21; they are published rows of the official archive. | Quarantine them as out of range. |
| D-017 | 2026-10-27 | Quarantine only rows that can't be used (invalid ID or date, missing product or company, duplicate ID); flag rows with soft issues and keep them. | Dropping complaints for a missing state or issue would understate totals. The profile shows no row breaks a hard rule today. | Quarantine every row with any empty field. |
| D-018 | 2026-10-27 | Map the 21 product names to stable product groups in a seed file; "Credit card or prepaid card" maps to Credit card. | The CFPB renamed products in April 2017 and August 2023, which breaks trends by product name. | Group by the published product name. |
| D-019 | 2026-10-27 | Keep narratives in their own table and flag `has_narrative` on each complaint. | Narratives are long text most questions don't need, and their coverage falls from about 42% (2018-2022) to 0% by August 2026. | Keep the narrative in the fact table. |
| D-020 | 2026-10-27 | Keep a bronze table of every published row as text, with its batch_id, and build everything else from it with dbt. | Types and rules live in one place (staging), and the warehouse can be rebuilt without re-reading the zips. | dbt reading the CSV files directly. |
| D-021 | 2026-10-27 | When a Complaint ID repeats, keep the copy from the latest export and quarantine the others. | A later export is the newer publication of the complaint. The profile found no repeats, so this only guards future loads. | Quarantine every copy. |
| D-022 | 2026-10-27 | Name the project QueryCF (repository `query-cf`, Python package `query_cf`), replacing the working name Complaint Radar. | It says what the project does, querying consumer finance complaints, and reads well on a CV next to "text-to-SQL". | Complaint Radar; Complaint Compass. |
| D-023 | 2026-10-28 | Record the exports each source config lists, and fail `load` and the dbt build when one has no landed batch. | The completeness check only compared batches the audit knew about, so a whole export missing from the audit would have passed silently. Found while checking a status listing. | Rely on the per-batch counts alone. |
| D-024 | 2026-10-29 | Write the semantic layer as plain YAML in `semantic/`, with a small query builder in `query_cf/semantic.py`. | Easy to read, review and explain, with no new dependency; it can move to dbt's semantic layer later. | dbt MetricFlow, which is heavier and unproven with this DuckDB 2.0 setup on Windows. |
| D-025 | 2026-10-29 | When a defined metric answers a question, the query builder writes the SQL, so the same request always gives the same SQL. | Answers are reproducible and reviewable; the model only has to choose metrics, groupings and filters. | Let the model write every query. |
| D-026 | 2026-10-29 | Move the five prepaid sub-products of "Credit card or prepaid card" to the Prepaid card group (refines D-018). | About 19,500 of its 206,356 complaints are prepaid cards; this keeps both groups unbroken from 2014 to 2026. | Keep the whole product in Credit card. |
| D-027 | 2026-10-29 | Match companies by exact published name, through a list of short names, never by part of a name. | "CITI" also matches Citizens Financial Group and Tri-Cities Finance; "DISCOVER" matches Account Discovery Systems. | Substring or fuzzy matching. |
| D-028 | 2026-10-29 | Define "accounts opened without consent" per taxonomy era, and state that bank accounts are covered only from April 2017. | Before April 2017 bank account complaints have no sub-issues, so there is no such category to select. | One list of issue names with no warning. |
| D-029 | 2026-10-29 | Rates leave out open complaints and outcomes that say nothing about relief; no days-to-company metric. | 476,090 complaints from 2026 were still open when the archive was published; the median days to the company is 0 in every year since 2015. | Count every complaint in the denominator. |
